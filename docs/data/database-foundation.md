## Role model

Runtime and migration privileges are separated:

- `nexora_app` — synchronous API runtime capabilities;
- `nexora_worker` — background worker capabilities;
- `nexora_migrator` — schema/migration capabilities only.

Passwords, connection strings and login credentials are never committed to Git. The repository bootstrap defines capability roles/grants; physical login credentials are provisioned through Neon and secret-management surfaces.

### Least privilege baseline

`nexora_app` and `nexora_worker`:

- may connect and use the application schema;
- receive only required DML privileges on owned application objects;
- cannot create/drop schemas or alter tables;
- cannot manage roles;
- cannot bypass tenant isolation by design.

`nexora_migrator`:

- owns or can assume ownership of the application schema/migration objects;
- executes ordered versioned migrations;
- is not used as an application runtime credential.

## Schema ownership

The application schema is `nexora`.

Rules:

1. avoid using `public` for application-owned tables;
2. every tenant-scoped table includes `tenant_id`;
3. foreign keys and uniqueness constraints include tenant dimensions where cross-tenant association would otherwise be possible;
4. RLS is defense in depth, not a substitute for application authorization;
5. migrations are the only supported way to change persistent schema;
6. runtime roles never execute ad-hoc DDL.

## Migration strategy

- one ordered migration history in the monorepo;
- forward-only by default;
- expand/contract for breaking or destructive changes;
- test migrations on an isolated Neon branch before production;
- verify a clean database can be created from zero;
- review SQL generated by Drizzle before application;
- explicit SQL is allowed for PostgreSQL features such as RLS, advanced constraints and indexes;
- production migrations use the migrator credential only.

## Seeds and fixtures

- synthetic data only by default;
- production data is not copied to lower environments without an approved sanitization process;
- seeds must be idempotent or explicitly resettable;
- no secrets, customer documents or real personal/financial data in repository fixtures.

## Backup / restore

Before production readiness, NEX-79 must validate:

- point-in-time recovery / retained history expectations;
- recovery procedure and access ownership;
- restoration into an isolated branch/project before destructive production recovery;
- recovery time and recovery point objectives;
- evidence that application schema and required data can be restored.

## Destructive changes

Drops, incompatible type changes, destructive rewrites and irreversible data transformations require the destructive-change checklist under `docs/runbooks/` and an explicit rollback/recovery plan.
