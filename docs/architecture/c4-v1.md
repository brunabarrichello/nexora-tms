# Nexora TMS — C4 Architecture v1

**Status:** Accepted Wave 0 baseline  
**Jira:** NEX-17 / NEX-62

## Principles

1. Modular monolith first; extract services only when evidence justifies it.
2. Separate deployables for Web, API and Worker.
3. Multi-tenancy from the first migration.
4. Security by default: authentication, authorization, audit, least privilege and isolation.
5. Explicit API, module, event and integration contracts.
6. Reproducible, versioned database migrations.
7. Reliable asynchronous processing through outbox, idempotency and retry.
8. Native observability with correlation IDs, structured logs, metrics and health checks.

## System context

Nexora TMS is the authority for transport operations, tenant memberships and business permissions, freight, capacity, contracting, trips, documents, operational finance and audit.

Primary actors:

- transport operations;
- commercial team;
- finance;
- compliance/risk;
- managers;
- tenant administrators;
- drivers/partners through future channels.

External systems are integrated through explicit adapters and contracts: managed identity provider, communications providers, tracking/telemetry, customer/partner APIs and webhooks, and future financial providers.

## C4 Level 2 — containers

### `apps/web`

- Next.js App Router + React + TypeScript.
- Target runtime: Vercel.
- Owns browser UI, navigation, forms, dashboards and session UX.
- Consumes published API contracts only.
- Never accesses PostgreSQL directly.

### `apps/api`

- NestJS + TypeScript.
- Target runtime: Railway.
- Primary transactional authority.
- Resolves identity and mandatory tenant context.
- Enforces RBAC/authorization and domain invariants.
- Persists transactional state and outbox records.
- Publishes versioned REST/OpenAPI contracts.
- Audits sensitive actions.

### `apps/worker`

- NestJS standalone + TypeScript.
- Target runtime: persistent Railway process.
- Handles durable jobs, retries, idempotency, notifications, documents, webhooks, integrations and scheduled work.
- Tenant-scoped jobs carry `tenant_id`, correlation ID and an idempotency identifier.

### Neon PostgreSQL

- System of record.
- Owns integrity, constraints, transactional outbox, audit persistence and tenant-scoped data.
- Runtime application, worker and migration processes use distinct least-privilege roles.
- RLS may be used as defense in depth according to ADR-0002.

### Object storage

- Stores document/evidence binaries.
- PostgreSQL stores metadata, ownership and authorization state.
- Access uses short-lived signed URLs or authorized streaming.
- Provider is hidden behind an adapter.

## Main flows

### Synchronous request

1. User authenticates through the managed identity boundary.
2. Web calls API.
3. API validates identity, membership, tenant and permission.
4. Use case enforces domain rules.
5. Transaction persists state and, when needed, an outbox record.
6. API returns a public DTO, never an ORM/entity object.

### Asynchronous event

1. State change and outbox entry commit in the same transaction.
2. Worker obtains the event durably.
3. Worker validates event ID, tenant ID, type and version.
4. Idempotent handler executes.
5. Retry/failure state is persisted and auditable.

### Document

1. API authorizes the operation.
2. Binary is uploaded through a controlled storage flow.
3. Metadata and entity ownership are persisted.
4. Future access requires tenant context and permission.
5. Retention policy governs physical deletion.

## Trust boundaries

| Boundary | Baseline rule |
| --- | --- |
| Browser → Web/API | Treat all input as untrusted; authenticate, authorize and validate payloads. |
| Web → API | Web is never the authority for permissions or tenant context. |
| API/Worker → DB | Separate roles, least privilege, migrations outside runtime role. |
| API/Worker → external systems | Timeouts, controlled retry and payload validation. |
| Object storage | Possession of an object key/URL does not grant business authorization. |
| Tenant A ↔ Tenant B | Cross-tenant access is forbidden, including indirect ID-based access. |

## Non-functional baseline

- mandatory tenant isolation;
- deny-by-default authorization;
- structured logs with correlation ID;
- no secrets in code, logs or documentation;
- reproducible migrations from a clean database;
- backup/restore validation before production;
- health/readiness endpoints;
- idempotency for events, webhooks and critical commands;
- audit of authentication, authorization and sensitive changes;
- negative cross-tenant tests;
- versioned API contracts;
- end-to-end correlation across Web/API/Worker.
