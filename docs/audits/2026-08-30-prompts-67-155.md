## PR review findings — Wave 0018

### Positive

- document metadata and versions are separated;
- version/validation histories are append-oriented;
- tenant context wraps database work;
- entity links resolve inside the active tenant/RLS boundary;
- dynamic table/column use in the reviewed service is constrained by internal allowlists/unions rather than arbitrary request strings;
- document row locking serializes version-number allocation for a document;
- storage is behind a port/adapter and the unconfigured adapter fails closed;
- database and document-specific Neon gates were included before promotion.

### P1 — authorization beyond tenant membership

`DocumentsController` is protected by the tenant runtime gate, but create/update/delete/upload/validate/link operations do not yet declare business permissions such as `documents.read`, `documents.manage`, `documents.validate` or scoped variants.

This is not a cross-tenant isolation failure: RLS still protects the tenant boundary. It is a least-privilege/business-authorization gap inside an allowed tenant and must be closed before production authorization is considered complete.

### P2 — upload verification ordering

`commitUpload` verifies the storage upload before acquiring/validating the database document row. The storage adapter must continue to scope verification by tenant + document and remain side-effect free. A future hardening change can validate the document first, then verify storage, then re-lock during commit if the chosen object-storage semantics allow it.

## PostgreSQL/platform findings

### Strengths

- PostgreSQL 18;
- explicit Drizzle migration journal;
- 20 migrations after Wave 0019;
- 96 expected application tables, with 88 tenant-scoped RLS tables;
- tenant-aware composite foreign keys in sensitive relations;
- dedicated `nexora_app` runtime role;
- API database pool is bounded/configurable;
- migrations are promoted by audited manifests rather than arbitrary production SQL.

### Production-readiness gaps observed

- the Neon default/main branch was observed as unprotected;
- public database connections were not globally blocked by project policy;
- no IP allowlist was configured at project level;
- observed history retention was 6 hours;
- no read replica or cross-region failover target was evidenced in the inspected configuration.

These facts do not make development/staging invalid. They mean DR/failover and database perimeter controls must be explicitly designed, tested and matched to the production plan before production approval.

## Authorization target model

The canonical path is:

```text
OIDC identity
  -> Nexora external identity
  -> active tenant membership
  -> tenant context
  -> RLS
  -> role permission
  -> organization/business-unit scope
  -> explicit resource/domain attribute when required
  -> allow/deny
```

Deny by default. Browser claims never grant Nexora business permissions.

## Missing role-per-organization capability

Current tables assign roles to a membership and organization/unit scopes separately. That is sufficient for a tenant-wide role restricted to selected scopes, but not for different roles in different organizations.

When RBAC implementation resumes, model a role binding with optional organization/business-unit scope (or an equivalent normalized binding table) rather than adding ad-hoc role columns to users or organizations. This change requires its own ADR/migration/gates and must not be slipped into an unrelated functional Wave.

## Integration-test target

Add an automated non-production smoke path that proves:

1. database migration succeeds from clean PostgreSQL;
2. API boots with the runtime role;
3. OIDC/auth test principal is resolved;
4. tenant A CRUD works;
5. tenant B cannot access tenant A data;
6. permission denial works inside the same tenant;
7. Web server can call the API;
8. worker starts without recursive scripts and can reach its dependencies;
9. rollback/known-good deployment path is documented and testable.

## Priorities

### P0 before production

- complete permission enforcement in the API (RBAC + typed contextual scopes);
- protect critical database branches and align provider/network controls with the production threat model;
- verify backup/PITR retention against the accepted RPO;
- execute and time a restore drill;
- establish a real rollback/failover test target before claiming regional failover;
- add end-to-end non-production smoke automation.

### P1 functional evolution

Continue the planned operational Waves for persistent/explainable Matching, complementary Negotiation, Trips execution and transversal audit. These can continue in development/staging while explicitly deferred production hardening remains visible and gated.

## Completion rule

No item is marked production-ready solely because its code exists. Production readiness requires evidence for functional behavior, persistence, tenant isolation, authorization, failure handling, observability, recovery and controlled promotion.
